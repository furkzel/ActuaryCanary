# 0811 — Gate v1.3: the demo carries every feed and a confirmed profile, the tiny fixtures stay

## Context
Records 0382 and 0383 moved the reinsurance treaties, reinsurance transactions, recoveries and ledger of every scenario into the scenario folder, but the committed examples and the tiny fixtures were older than the generator. Release 1.3.0 should show M07 to M10 in its demo.

## Decisions
- **The tiny fixtures and the baseline and messy_headers examples are NOT regenerated (deviation from the item text).** They were regenerated once and reverted: the regenerated tiny baseline holds the ledger and the treaties, and 25 tests (14 of the fast suite) read it as the ledger-free tiny set (M08 and M10 skipped, 'no expenses', the file list, the injected faults only, the guide), and the golden copy moved by hundreds of leaves, against the condition of the item that the golden moves only by version strings and run ids. Rewriting those tests belongs to a fix item with `just synth-fixtures` (list in the criteria table). The golden test had also become flaky with the regenerated fixture (see the findings below). `test_files.py` requires the examples and the fixtures to hold the same six feeds, which is why the two move together.
- **The demo scenario needs no change.** `synthetic/scenarios/demo.yaml` extends the baseline, which already switches on the treaties (QS_PROPERTY, XL_TPL, XL_PROPERTY_CAT with the surplus), the recoveries, the expenses and the ledger; the demo folder held all four feeds since record 0382. Only the shipped copy was missing.
- **What the refresh script now copies.** `docs/tools/refresh_examples.py` copies every top-level `*.xlsx` of a scenario folder (the ten feeds and any `_partN` workbook) into the demo, and for the demo also `phase2/interest_rates.xlsx`; baseline and messy_headers get the top-level workbooks of the committed tiny fixtures (the six feeds). It does not copy truth files, canonical copies, manifests or the other `phase2/` workbooks (life feeds): those stay with the fixtures, as before. Test: `tests/docs/test_refresh_examples.py` (a temporary folder, no generation).
- **The demo profile is confirmed (planner decision 4).** The run of the demo is made twice: the first saves the proposed ledger account-mapping profile, the script marks it confirmed on the generation date, the second (the committed one) reads it, so the M10 page says "confirmed on <date>" and not "proposed, not confirmed". The confirmed profile is committed beside the report (`examples/demo/report/ledger-cb3fe509454702ff.yaml`) so that a test can reproduce the committed run id. Baseline and messy_headers keep a proposed profile.
- **Two test premises changed.** `test_running_an_example_gives_the_run_id_of_its_committed_report` now seeds the profiles folder with the committed confirmed profile of the example (the run id depends on the profile's hash). `test_demo_equals_a_run_on_the_same_folder_by_fingerprints` runs `canary run` with its own empty profiles folder: the demo has saved its proposal in `./profiles`, and a second run on that folder reads it as saved (the saved/proposed state is a visible output), while the premise of the test is that both runs start from the same state. `test_the_demo_files_are_what_the_scenario_writes_today` now checks the ten feeds.

## Findings that fire on the demo
- KF44 for XL_TPL, 3 of 13 treaty years (2021, 2024, 2025): the booked amounts follow the occurrence-date clause and injected extreme payments, the platform's default is payment by payment (records 0403, 0408). Not a new defect.
- KF47: 65 of 2,400 entity-class-months differ materially (OUTSTANDING 48, CLAIMS_PAID 9, RI 4, PREMIUM 4); the written differences and the data faults (record 0423) and the RI rate convention of the generator (record 0423, carried from F2a) explain the classes; one suspense account is unmapped (DV-LDG-09).
- KF35 information. KF47's suggested cause for the largest gap is IBNR in the ledger outstanding.
- Not firing on the demo: the quota-share premium on gross, the excess-of-loss premium on written premium and the weekend FX rates (carried generator inconsistencies, records 0403, 0405, 0423); they are listed in `examples/README.md` and wait for the fix items.

## Findings for the fix items (not fixed here)
Two runs on the same inputs differ in the last digits of some floating-point sums (M08: `reinsurance_reconciliation.csv`, `measures.csv` RI03 values, e.g. 1856145.3503004801 against 1856145.35030048), so `canary demo` and `canary run` no longer give byte-identical manifests: `test_demo_equals_a_run_on_the_same_folder_by_fingerprints` compares bytes and fails on that (it passed while the demo had no treaties). The run ids are equal. The cause is probably the order of a parallel sum in the reinsurance code; a method change is outside this item. The test stays as it is and is listed as FAIL in the criteria table.

Also found, outside this item's area:
- **KF47's class counts are not in a fixed order when two classes tie** (`report/ledger_section.py`, `group_by(...).sort("len", maintain_order=True)` on an unordered group-by): "RI 8, CLAIMS_PAID 8" flipped between runs of the regenerated tiny baseline and made the golden test fail one run in three. A tie-break on the class name fixes it; the edit was not made (outside the area). The committed demo has the same tie (RI 4 and PREMIUM 4); its sentence may read the other way on the next run.
- **Stale slow tests** (premise changed by F1bc to F2b, not by this item; they fail today): `tests/test_pipeline.py::test_modules_without_their_files_are_skipped_with_the_reason` (M10 is skipped too), `tests/ui/test_end_to_end.py` (the Turkish run id of the tiny baseline is the one of 1.2.0, line 58; the demo through the interface has a proposed ledger profile while the committed demo is confirmed, so its run id differs by design), `tests/cli/test_demo.py::test_demo_equals_a_run_on_the_same_folder_by_fingerprints` (bytes, see above; it also reads the proposal saved by the first run).
