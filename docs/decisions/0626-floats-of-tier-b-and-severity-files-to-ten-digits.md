# 0626 — Floats of the tier B and severity files are written to 10 significant digits (CV06 1.1.0)

## Context
The pull request of `s/P25b-integration` failed on Ubuntu in `tests/report/test_golden.py` and passed on Windows. Five files of the tiny baseline run had another SHA-256 and size: `tier_b_ultimates.csv` (4,780 against 4,779 bytes), `tier_b_parameters.csv` (13,189 against 13,202), `severity_parameters.csv` (604 against 606), `severity_fits.csv` (hash only) and `severity_plots.csv` (33,986 against 33,993). The golden copy was written on Windows.

**How tier A is written.** There is no rounding convention for files: CV06 1.0.0 said "Exported data files carry unrounded values", and `write_csv` of polars writes the shortest text that reads back as the same float. The tier A files are equal on every platform because they hold sums, products and quotients of IEEE numbers. The only rounding in the golden test is `normalise()`, which takes the numbers of the report page to 10 significant digits. The writers of the new files (`write_output(..., table.write_csv())` in `pipeline.py`, and the parquet of the simulated reserves) kept the same convention, but their numbers come from linear algebra (BLAS), optimisers and the maths library, whose last bits differ by platform.

**What was run (2026-10-27).** The discrepancy was reproduced two ways, and compared file by file, cell by cell:
- On Windows, the BLAS thread count (1, 2, 4 threads) changes nothing. The BLAS kernel does: `OPENBLAS_CORETYPE=Sandybridge` (also Nehalem, Prescott) against the default kernel changes 40 cells of `tier_b_parameters.csv` and 11 of `tier_b_ultimates.csv`, by up to 1.05e-14 relative, and the file sizes by 5 and 0 bytes (13,189 and 13,194).
- On Linux: the Linux wheels of `uv.lock` (numpy 2.5.4, scipy 1.18.1, polars 2.0.0, installed by `uv pip install --python-platform x86_64-manylinux_2_28 --target <scratch>`, no system package) run by the Python 3.12.3 of WSL Ubuntu 24.04 gave the same five files different from Windows and no other output file: sizes 604/606, 13,189/13,193, 4,780/4,779, 33,986/33,987, `severity_fits.csv` equal in size. The sizes of the CI runner differ a little from these (its CPU and libm differ from the WSL machine), the set of files and the kind of difference are the same. Differences: `tier_b_*` up to 7.2e-15, `severity_fits.csv` 8.1e-15, `severity_plots.csv` 1.7e-15 (126 cells), all last bits; and `severity_parameters.csv`: the Pareto II standard errors of MOTOR_OD, 3.7e-7 relative.

**Cause of the 3.7e-7.** The standard errors come from a central-difference Hessian with a step of 1e-4 of each parameter (`numeric.numerical_hessian`); one last bit of the log-likelihood (1,661.76 has a spacing of 2.3e-13) divided by the squared step moves the standard errors: with a random one-bit error in each evaluation on a 120-claim Pareto II sample, the standard errors moved by up to 8.2e-6 relative. A platform that sums or takes logarithms differently is that one bit. On the demo the Pareto II fit of PROPERTY (shape 1.056, a flat likelihood) differs by 1.4e-7 in the estimate itself and 9.6e-6 in a standard error.

## Decision
- **One rule, written once.** Every 64-bit float of a table written by the tier B or severity methods is rounded to 10 significant digits (nearest decimal, as Python formats it, so the same on every platform; a negative zero is written as zero; null, NaN and infinity stay). The rule is `SIGNIFICANT_DIGITS`, `round_significant`, `round_floats`, `write_table` and `write_parquet_table` in `manifest/run.py`; the pipeline writes `tier_b_*`, `bootstrap_*`, `back_test.csv`, `severity_*`, `extreme_*` and the parquet files of the simulations through them, and nothing else rounds. A nested column is refused. The rows of MT11 to MT18, MT22 and AE02 in `diagnostics.csv` (a file shared with tier A) are rounded by `round_significant` through `ROUNDED_METHODS`; their text is not touched. The tables inside the program are not rounded (the tests at 1e-12 on them stand); only what is written.
- **Why 10.** The largest last-bit difference seen between platforms is 1.05e-14 relative. Ten digits leave a relative step of 1e-10 to 1e-9, four orders above it: a cell that differs by the observed noise lands on the other side of a rounding boundary with a chance of about 1e-5 to 1e-4. Ten digits are the tier A convention where one exists (`normalise()` of the golden test), and the tightest tolerance in the manifests of the tier B references is 1e-9, which the rounding error (at most 5e-10) stays below (the tests at 1e-12 compare the tables inside the program, which are not rounded). Fewer digits would throw away the precision of the amounts; the report shows whole currency units.
- **CV06 1.1.0** (owner approved in the session of 2026-10-27, with the move of every run id that follows from it, because the version of CV06 is part of the specification list of the run id): the exception for the files of MT11 to MT18, MT22 and AE02, and the default `file_significant_digits` 10. Every other data file stays unrounded.
- **Tests.** `tests/manifest/test_tables.py` (the rule, null/NaN/infinity/negative zero, the writers, the digits equal the spec default) and `test_no_float_of_a_new_file_has_more_digits_than_the_rule_allows` in `tests/test_pipeline_tier_b.py`: every float cell of every csv file of the tiny run except the named tier A files (`FULL_PRECISION_FILES`) and every float of the rows of the rounded methods in `diagnostics.csv`. A later item that writes a new csv file with `write_csv` fails it; a tier A file is added to the list on purpose. With the rounding switched off the file test and three writer tests fail (run once, restored).

## Result
- Windows against Linux, after the rule (the Windows run as the reference): tiny baseline: 38 of the 41 comparable files byte equal (`manifest.json` and `report.html` carry the hashes of the others); `severity_parameters.csv` still differs in 2 of 48 cells (the two Pareto II standard errors, 3.7e-7). Demo: `severity_parameters.csv` (4 of 192 cells, up to 9.6e-6), `severity_fits.csv` (2 of 288, 1.2e-7) and `severity_plots.csv` (248 of 22,788, 4.1e-7) still differ; every other file of MT11 to MT18, MT22 and AE02 (the simulated reserves of MT11 included) and `diagnostics.csv` is equal.
- **Files outside this record that also differ between platforms, not changed:** on the demo `reserve_range.csv` (12 of 1,584 cells) and `measures.csv` (12 of 68,247 cells, the RS03 Mack standard error and its coefficient of variation) differ by 3.7e-15 relative. They are tier A files, unrounded by CV06, and no golden or test holds their hash. They are the same kind of last-bit difference; rounding them is a decision for the owner.
- Rounding moved nothing beyond rounding: old against new run of the three examples, every cell of every changed file is within 5e-10 relative of the old value (baseline, messy_headers and demo: 12, 12 and 25 files), every tier A file and every text cell is byte equal.

## Not solved: the maximum-likelihood files (work item 6)
Ten digits cannot make the files equal where the platforms differ by 1e-7 to 1e-5: the standard errors of the numerical Hessian and the estimates of a flat likelihood (Pareto II with a shape near 1, the generalised Pareto). `severity_parameters.csv` (and, on larger data, `severity_fits.csv` and `severity_plots.csv`, which hold curves of the fitted parameters) therefore **still differ on Ubuntu**, and the golden copy holds the Windows hash of `severity_parameters.csv`. UNVERIFIED on the CI runner; the WSL run says it will fail there on that one file. No file was dropped from the golden copy. Alternatives for the owner, the first one recommended; none is implemented:
1. **Remove the noise at its source** (own item, amends MT17 and MT18): analytic second derivatives for the five families instead of the central differences, and a tighter convergence of the Pareto II and generalised Pareto fits. Standard errors and the flat-likelihood estimates move once, by up to about 1e-5; the benchmarks of MT17 and MT18 are run again and the golden copy is rewritten. After that 10 digits hold with the odds above.
2. **Hash the MLE-based files coarsely in the golden copy** (small, stops the red CI): the golden copy takes, for the files of MT17 and MT18, the SHA-256 of the file with its floats rounded to 5 significant digits (the file itself keeps 10). This lowers the odds but does not exclude a difference: a cell that differs by 4e-7 meets a rounding boundary of a 5-digit step (1e-5 to 1e-4) with a chance of a few per cent, and of tens of per cent at the 9.6e-6 of the demo.
3. **Compare those files by tolerance, not by hash** (every float within 1e-4 relative, text equal), the manifest keeping the real hash. Exact for the test, but the golden copy then stores the table, not a hash.
