# 0421 — The account-mapping profile

## Context
CV12 asks for a profile of rules (entity, account pattern, class, sign, balance kind, line) that the user confirms and reuses, whose fingerprint enters the manifest and the run id. M10 and DV-LDG-09 both read it. The UI is not touched in this item.

## Decisions
- **One YAML file per chart of accounts**, `ledger-<fingerprint>.yaml` in the profiles folder beside the column profiles (`ledger/profile.py`): pydantic model, save, read, SHA-256, editable by hand. The fingerprint is the first 16 hex digits of the SHA-256 of the sorted distinct account codes, so the same chart is recognised in the next run and entities with the same chart share the file. The file lists the accounts it stands for, as the column profiles list their headers, and a file whose fingerprint does not fit them is a profile error.
- **Order of precedence** of two rules that both match an account: the longer pattern (the characters before the star) wins; of the same length an exact code beats a prefix; of the same again a rule of an entity beats a general rule; two rules still equal are a profile error that is listed (`Assignment.ties`) and leaves those accounts out of the reconciliation and DV-LDG-09 counts them as not mapped. The entity rule is the planner's; CV12 states the first and the tie.
- **Confirmation without a screen.** With no saved profile the run proposes one, saves it with `confirmed_on` empty when it has a profiles folder, and uses it labelled "proposed, not confirmed". The owner confirms by setting `confirmed_on` in the file (the file's header says so). A command-line option would be in `cli/`, outside this item; the editing route needs none. The profile's SHA-256 (of the file's bytes when it was read, of the text `save_profile` writes when proposed) is a determinant of the run id (entry `ledger_account_mapping` of the mappings applied) and is written in the manifest under `account_mapping` (fingerprint, SHA-256, status, `confirmed_on`, file, rule count), only when the run has a ledger. Confirming the profile therefore changes the run id; runs without a ledger keep theirs.
- **The proposal** (`ledger/proposal.py`) classes each account code from the `account_class` column (the most frequent class, labels outside the classes ignored), else from the words of `account_name` (`ledger/classes.py`, `NAME_TOKENS`, first match, a token of three letters or fewer must be the whole name). The sign is the sign of the sum of the account's balances (a magnitude positive for the platform; CV12's default only when they sum to zero); the balance kind is PERIOD for the stocks (OUTSTANDING, UPR) and otherwise YEAR_TO_DATE when the opening balance of the first fiscal month is zero after a month with a balance (the restart that DV-LDG-07 already accepts) or, without opening balances, when the balance climbs within the fiscal year in 80 % of the steps and restarts at its start. Patterns are the exact codes. Accounts the proposal cannot class are not in the profile. On the tiny scenarios it reproduces `truth/ledger_mapping_profile.csv` for every account (resolved, not as text, because the truth writes `600*` and the proposal `600`); without opening balances it reads RI and the change-in-provisions account as PERIOD, which a person corrects: the proposal is a proposal.
- **Name tokens are not alias entries.** CV12 points to AL04; a value entry of the alias files belongs to a field with a closed list of classes in `spec/data` and is checked against it, and `account_name` is free text. No entry is added to `spec/aliases`; the words live in one table in the package, tested. The class labels of the `account_class` column are AL02's (moved from AL04 in F1bc) and unchanged.
- **Balances** (`ledger/balances.py`): the profile's sign turns a balance into the platform's magnitude; PERIOD balances are used as given (stocks at the period end); YEAR_TO_DATE balances are differenced against the closing balance of the month before in the same entity, account and currency, or against the row's opening balance when that month is missing, or taken as they are in the first month of the fiscal year (`fiscal_year_start_month` of the run, CV04); when neither the month before nor an opening balance exists the movement is not told (null) and the month is not reconciled.
- **DV-LDG-09** is evaluated: an account with a non-zero balance that the profile of the run does not map (or maps ambiguously) is a finding with the account, the entity and the latest balance, and the profile's state ("proposed, not confirmed", "confirmed", or "no saved profile: the proposal is used" for a check run without a profile, as the data-rule tests do). `Context` and `evaluate` carry the profile as an optional argument; the `NOT_BUILT` list stays, empty. `spec/data/ledger.yaml` 0.2.0.

## Consequences
- The old test that expected DV-LDG-09 to be "not built" is rewritten with a case of its own (premise changed).
- A ledger with a split by line is not mapped by line yet: the rule's `line` is kept in the file and in the amounts, the proposal leaves it empty.
